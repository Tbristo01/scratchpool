# Repository controls

These are the checks and balances on how code gets into scratchpool and how releases get out. Each row says what the control prevents and a command anyone (or the maintainer, where admin access is needed) can run to verify it. Commands use the [GitHub CLI](https://cli.github.com/); `R=Tbristo01/scratchpool`.

Some settings are on the repository rather than in files, so they can drift. If a verify command disagrees with this page, the page is wrong or the setting changed: open an issue.

| Control | Where | What it prevents | How to verify |
|---|---|---|---|
| **Branch protection on `main`** | Repo settings | Any change reaching `main` except through a pull request, including the maintainer's (a PR is required, with 0 required approvals while there is one maintainer); direct pushes, force pushes and deletion of `main`; merge commits (linear history); merging with unresolved review conversations. Enforced for admins too (`enforce_admins`), so no one can bypass it without first changing the setting, which is audit-logged. | `gh api repos/$R/branches/main/protection --jq '{pr_required: (.required_pull_request_reviews != null), approvals: .required_pull_request_reviews.required_approving_review_count, enforce_admins: .enforce_admins.enabled, linear: .required_linear_history.enabled, force: .allow_force_pushes.enabled, delete: .allow_deletions.enabled, conversations: .required_conversation_resolution.enabled}'` (expect `true`, `0`, `true`, `true`, `false`, `false`, `true`) |
| **Required status checks** | Repo settings, [ci.yml](../.github/workflows/ci.yml), [dependency-review.yml](../.github/workflows/dependency-review.yml), code scanning | Merging a PR unless all 11 checks pass on a branch that is up to date with `main` (strict): `test (ubuntu-latest, node 20)`, `test (ubuntu-latest, node 22)`, `test (macos-latest, node 20)`, `test (macos-latest, node 22)`, `test (windows-latest, node 20)`, `test (windows-latest, node 22)`, `validate manifests`, `secret-pattern scan`, `shellcheck examples` (the 9 [ci.yml](../.github/workflows/ci.yml) jobs), `dependency review` ([dependency-review.yml](../.github/workflows/dependency-review.yml)) and `CodeQL` (code scanning). Job names are the check names, so renaming a CI job silently drops a required check; don't. | `gh api repos/$R/branches/main/protection/required_status_checks --jq '{strict, n: (.checks \| length), contexts: [.checks[].context]}'` (expect `strict: true`, `n: 11`) |
| **Squash-only merges** | Repo settings | Merge commits and rebase merges. Every PR lands as one squash commit that GitHub creates and signs with its own key, so it satisfies the signed-commit requirement whether or not the contributor signed their commits. Merged branches are deleted. | `gh api repos/$R --jq '{allow_squash_merge, allow_merge_commit, allow_rebase_merge, delete_branch_on_merge}'` (expect `true`, `false`, `false`, `true`) |
| **CI hygiene** | [ci.yml](../.github/workflows/ci.yml) | Hung jobs burning minutes (every job has `timeout-minutes`); stale PR runs (a new push cancels the PR's superseded run). Pushes to `main` are never cancelled, so every commit on `main` has a full CI record. | `grep -n 'timeout-minutes\|concurrency' -A2 .github/workflows/ci.yml` |
| **Tag ruleset** | Repo rulesets ("protect release tags") | Moving, force-updating or deleting a `v*` tag after it is pushed, so a published release always points at the commit it was built from. The ruleset has no bypass actors: not even a repository admin can move or delete a release tag without first editing the ruleset (audit-logged). | `gh api repos/$R/rulesets --jq '.[] \| {id, name, target, enforcement}'` then `gh api repos/$R/rulesets/<id> --jq '{enforcement, conditions, rules: [.rules[].type], bypass_actors}'` (expect `active`, `refs/tags/v*`, `deletion`/`non_fast_forward`/`update`, `bypass_actors: []`) |
| **CODEOWNERS** | [.github/CODEOWNERS](../.github/CODEOWNERS) | Changes to the skill, workflows, manifests or security policy landing without the owner being asked to review. With one maintainer it routes reviews; it does not require approval (`require_code_owner_reviews` is off, see [GOVERNANCE.md](../GOVERNANCE.md) for when that changes). | `gh api repos/$R/codeowners/errors` (expect `"errors": []`) |
| **Release environment approval** | Repo environment `release`, [release.yml](../.github/workflows/release.yml) | Publishing a release without a human check: the `release` job, the only job with write access, waits for @Tbristo01's approval and can only deploy from `v*` tags, never from a branch. Admins cannot bypass the approval (`can_admins_bypass` is off). | `gh api repos/$R/environments/release --jq '{can_admins_bypass, rules: [.protection_rules[] \| {type, reviewers: [.reviewers[]?.reviewer.login]}]}'` (expect `can_admins_bypass: false`) and `gh api repos/$R/environments/release/deployment-branch-policies --jq '.branch_policies[] \| {name, type}'` (expect `v*`, `tag`) |
| **Build provenance attestations** | [release.yml](../.github/workflows/release.yml) | A skill zip that was swapped, rebuilt elsewhere or uploaded by hand passing as an official release. Each zip carries a signed SLSA provenance statement naming this repo, workflow and commit. | `gh attestation verify scratchpool-skill-<v>.zip --repo Tbristo01/scratchpool --signer-workflow Tbristo01/scratchpool/.github/workflows/release.yml --source-ref refs/tags/v<v>` (see [RELEASING.md](../RELEASING.md)) |
| **Checksums** | [release.yml](../.github/workflows/release.yml) | Corrupted or truncated downloads. | `sha256sum -c SHA256SUMS` in the folder holding the downloaded release assets |
| **Release notes from CHANGELOG** | [release.yml](../.github/workflows/release.yml) | Releases whose notes drift from CHANGELOG.md, or a tag with no changelog entry (the release fails). | `gh release view <tag> --json body --jq .body` and compare with the `## [<v>]` section |
| **Version consistency** | [ci.yml](../.github/workflows/ci.yml), [release.yml](../.github/workflows/release.yml) | Shipping a zip whose `plugin.json`, `package.json` or `SKILL.md` version disagrees with the tag. CI (`validate manifests`) checks all three agree on every PR, so a mismatch is caught before a tag is pushed; the release workflow checks them against the tag. | The `validate manifests` check on any PR, and the "Check tag matches" step in any release run: `gh run view <run-id> --log` |
| **Secret scanning and push protection** | Repo security settings | Pushing commits that contain known credential formats (push protection blocks the push) and leaving leaked secrets unnoticed (alerts). Complements the CI `secret-pattern scan`, which also catches Salesforce auth URL and token shapes. | `gh api repos/$R --jq '.security_and_analysis \| {secret_scanning, secret_scanning_push_protection}'` |
| **Dependabot** | Repo security settings, [dependabot.yml](../.github/dependabot.yml) | Running actions with known vulnerabilities (alerts and security update PRs) and pinned action SHAs going stale (one grouped weekly PR for all action bumps, labelled `dependencies` and `github_actions`, prefixed `ci:`). | `gh api repos/$R/vulnerability-alerts -i \| head -1` (expect `204`) and `gh api repos/$R --jq '.security_and_analysis.dependabot_security_updates'` |
| **Dependency review** | [dependency-review.yml](../.github/workflows/dependency-review.yml) | Merging a PR that adds a dependency of any scope (runtime, development or unknown) with a known advisory of moderate severity or higher, or a runtime dependency under a license Apache-2.0 cannot redistribute (allow list: Apache-2.0, MIT, MIT-0, BSD-2/3-Clause, ISC, 0BSD, BlueOak-1.0.0, CC0-1.0, Unlicense, Zlib, Python-2.0). It is a **required** status check, so a failure blocks the merge. The CI "zero runtime dependencies" step, also required, still rejects any runtime dependency at all. | The `dependency review` check on any PR: `gh pr checks <n>`; it is listed in `gh api repos/$R/branches/main/protection/required_status_checks --jq '[.checks[].context]'` |
| **CodeQL** | Repo code scanning (default setup) | Common JavaScript/TypeScript, Python and GitHub Actions workflow vulnerability patterns (injection, incomplete escaping, unsafe path handling, untrusted input in workflow expressions) merging unnoticed. `CodeQL` is a **required** status check, and open alerts are triaged: fixed in code where possible, dismissed only as a false positive with a written justification. | `gh api repos/$R/code-scanning/default-setup --jq '{state, languages}'` (expect `configured`) and `gh api 'repos/$R/code-scanning/alerts?state=open&tool_name=CodeQL' --jq length` |
| **OpenSSF Scorecard** | [scorecard.yml](../.github/workflows/scorecard.yml) | Supply-chain posture regressing silently (unpinned actions, broad token permissions, missing branch protection). Runs on every push to `main`, weekly and when branch protection changes; results go to code scanning and the public badge in the README. | `gh run list --workflow scorecard --limit 1` and the badge at <https://scorecard.dev/viewer/?uri=github.com/Tbristo01/scratchpool> |
| **Least-privilege tokens** | Repo Actions settings, every workflow | A compromised step using the `GITHUB_TOKEN` to push code or tamper with releases. The default token is read-only; each workflow declares `contents: read` (Scorecard: `read-all`) at the top and widens only per job (`pull-requests: write` to comment a failed dependency review, `security-events`/`id-token: write` for Scorecard, `contents`/`id-token`/`attestations: write` for the release job). Checkouts use `persist-credentials: false`. | `gh api repos/$R/actions/permissions/workflow --jq '{default_workflow_permissions, can_approve_pull_request_reviews}'` (expect `read`, `false`) and `grep -n -A4 'permissions:' .github/workflows/*.yml` |
| **Pinned actions** | Repo Actions settings, every workflow | A moved or hijacked action tag running new code in CI or the release job. Every `uses:` is a full 40-character commit SHA with the release tag in a trailing comment, and the repository enforces it (`sha_pinning_required`): a workflow that references an action by tag or branch fails to run. Dependabot proposes updates. | `gh api repos/$R/actions/permissions --jq .sha_pinning_required` (expect `true`) and `grep -hn 'uses:' .github/workflows/*.yml \| grep -vE '@[0-9a-f]{40} # v'` (expect no output) |
| **Actions allowlist** | Repo Actions settings | Workflows pulling in arbitrary third-party actions. Only GitHub-owned actions, actions from verified creators, and `ossf/scorecard-action`, `ludeeus/action-shellcheck` and `softprops/action-gh-release` may run. | `gh api repos/$R/actions/permissions --jq .allowed_actions` and `gh api repos/$R/actions/permissions/selected-actions` |
| **Signed commits** | Repo settings | Unsigned or unverified commits on `main`. `required_signatures` is on, so every commit on `main` must carry a verified signature. With squash-only merges that commit is the one GitHub creates and signs, so contributors do not need to sign their own branch commits (signing is still encouraged). | `gh api repos/$R/branches/main/protection/required_signatures --jq .enabled` (expect `true`) and `gh api repos/$R/commits/main --jq .commit.verification.verified` (expect `true`) |
| **Admin enforcement** | Repo settings | The repository admin bypassing branch protection: `enforce_admins` is on, so the PR, signature, linear-history and required-check rules apply to the maintainer too. An emergency (for example, a broken required check) is handled by a PR that fixes the check; if a setting ever has to be relaxed, that change is audit-logged and is reverted in the same session. | `gh api repos/$R/branches/main/protection/enforce_admins --jq .enabled` (expect `true`) |

## Proof

The settings above are enforced, not just configured. On 2026-10-02 a direct push to `main` by the repository admin was rejected by GitHub:

```text
remote: error: GH006: Protected branch update failed for refs/heads/main.
remote: - Changes must be made through a pull request.
remote: - Commits must have verified signatures.
```

To re-check every enforced setting in one go:

```sh
R=Tbristo01/scratchpool
gh api repos/$R/branches/main/protection --jq '{enforce_admins: .enforce_admins.enabled, required_signatures: .required_signatures.enabled, pr_required: (.required_pull_request_reviews != null), linear: .required_linear_history.enabled, conversations: .required_conversation_resolution.enabled, strict: .required_status_checks.strict, checks: [.required_status_checks.checks[].context]}'
gh api repos/$R --jq '{allow_squash_merge, allow_merge_commit, allow_rebase_merge}'
gh api repos/$R/environments/release --jq .can_admins_bypass
gh api repos/$R/rulesets --jq '.[] | select(.target == "tag") | .id' | xargs -I{} gh api repos/$R/rulesets/{} --jq '{enforcement, bypass_actors}'
gh api repos/$R/actions/permissions --jq .sha_pinning_required
```

Expected: `enforce_admins`, `required_signatures`, `pr_required`, `linear`, `conversations` and `strict` all `true` with the 11 checks listed above; squash only; `false` for `can_admins_bypass`; `active` with `bypass_actors: []`; `true` for SHA pinning.

## What these controls do not cover

- **The maintainer.** With one maintainer, branch protection requires a PR and checks, not a second person's review. Nothing here has an admin bypass, but the admin can still change the settings themselves; every such change is in the audit log. The release environment approval and provenance attestations make every release a deliberate, traceable act by that maintainer; they cannot stop a malicious maintainer. [GOVERNANCE.md](../GOVERNANCE.md) describes how review requirements tighten when a second maintainer joins.
- **Your machine.** scratchpool runs locally with your own `sf` auth. Its runtime security model is in [security.md](security.md).
